# Security review: clients module

**Date:** 2026-10-04
**Scope:** `apps/api/src/clients/`, `apps/api/src/common/validation/country-codes.ts`,
the DATE parsing in `apps/api/src/database/database.ts`, migrations
`0010`–`0013`. Commits `e35023b`…`4f73108`.
**Method:** code read against the review checklist in the engineering rules;
each safeguard confirmed by breaking it on purpose and checking a test fails;
uncertain points settled by probes against the real app and PostgreSQL with
synthetic data.

## Findings

### C1 — Control and text-direction characters accepted in text fields

| | |
|---|---|
| Severity | **Medium** |
| Location | Text fields of `POST /clients`, `PATCH /clients/:id`, contacts, take-over reason |
| Problem | Names, address lines, job titles and reasons accepted line breaks, tabs, right-to-left overrides and invisible-only values. A null byte reached PostgreSQL and gave a 500. |
| Impact | An override makes a name display differently from what is stored (the characters after U+202E show reversed), which can mislead someone checking identity or conflicts. A line break in a name can later split a letter or an email header. **Probe:** all four kinds were accepted with 201; the null byte gave 500. The logged database error was `invalid byte sequence for encoding "UTF8": 0x00`, without the value. |
| Fix | **Fixed in this review.** Every free-text field refuses control characters (`\p{Cc}`) and direction overrides and isolates (U+202A–U+202E, U+2066–U+2069), and must contain a letter or a digit. |
| Test | `clients.controller.spec.ts`: null byte, line break, override, invisible-only name, tab in an address, line break in a job title, null byte in a reason. Removing the check fails all six. |

### C2 — The firm's client list can be collected through search, unnoticed

| | |
|---|---|
| Severity | **Medium** |
| Location | `GET /clients/search` |
| Problem | Search is firm-wide by design, so people can avoid duplicates. Nothing limits how often it is used, and searches are not recorded. |
| Impact | Who a law firm acts for is confidential. **Probe:** one fee earner sent all 676 two-letter searches in 5.3 seconds and collected 348 distinct clients of the 2,103 in the test database, which is full of repeated names. With real names, and three-letter searches (about 17,500 requests, a few minutes), most of a firm's client list would come out, and nothing would show it happened. |
| Fix | **Fixed after the review**, by decision of the project owner: at most 60 searches per person per hour (429 with `Retry-After` after that). Each search is recorded as `client.searched` with its number of results, never the text; that record is what the limit counts, so there is no second store to keep in step. Going over is recorded once an hour as `client.search_limited`. A per-person advisory lock makes parallel searches queue. |
| Test | `clients.controller.spec.ts`: "limit and record". 70 searches sent at once give exactly 60 answers and 10 refusals. Removing the limit, removing the lock, or recording the text each fail a test. |

### C3 — A client is stranded when its responsible person changes role but stays active

| | |
|---|---|
| Severity | **Low** (operational, and confidentiality of oversight) |
| Location | `ClientsService.takeOver`, the takeover trigger in `0012_client_takeover.sql` |
| Problem | Takeover is allowed only when the responsible person's account is disabled. Someone moved from fee earner to the accounts team keeps an active account but loses `clients.view`. |
| Impact | **Probe:** after the role change, the creator got 403, a partner got 404, and the partner's takeover got 409. Nobody could reach the client until Matters adds teams. |
| Fix | **Fixed after the review**, by decision of the project owner: a takeover is also allowed when the responsible person no longer holds `clients.view`. Checked in the service from the permission table, and in the trigger (migration `0014`) from its own role list. |
| Test | `clients.controller.spec.ts`: takeover from someone moved to accounts. `clients.migration.spec.ts`: the trigger agrees with the permission table for every role. Reverting the service check fails a test; with the service allowing everything, the database still refuses. |

### C4 — The database does not refuse control characters itself

| | |
|---|---|
| Severity | **Low** (defence in depth) |
| Location | Check constraints in `0010`, `0013` |
| Problem | Every other rule on client text is enforced twice, by the API and by the database. C1's rule is in the API only. |
| Impact | A future code path that writes client text without the API's schemas could store unsafe characters. |
| Fix | **Open:** a migration adding `CHECK (column !~ '[[:cntrl:]]')` and the direction-override range to each text column. |
| Test | Database tests like the existing check-constraint cases. |

### C5 — Search reads every client

| | |
|---|---|
| Severity | **Low** (availability) |
| Location | `ClientsRepository.search` |
| Problem | `ILIKE '%text%'` cannot use a normal index, so each search scans all clients. |
| Impact | Fine for thousands of clients; slow for very large ones, and combined with C2 a source of load. |
| Fix | With conflict checks in Matters: `pg_trgm` trigram index, which also catches spelling variations. |
| Test | Query plan check once the index exists. |

### C6 — Client personal data relies on disk encryption

| | |
|---|---|
| Severity | **Low** now, a production requirement |
| Location | `client_individuals`, `client_contacts` |
| Problem | Dates of birth, addresses, emails and phone numbers are stored as plain columns. |
| Impact | Anyone with a copy of the database files or a backup reads them. |
| Fix | **Before production:** encrypted storage and encrypted, access-controlled backups (see `disaster-recovery.md`). Column encryption is not proposed: it would stop search and checks, and does not help against the app's own access. |
| Test | Deployment checklist. |

### C7 — Take-over answers for any client id

| | |
|---|---|
| Severity | **Informational** |
| Location | `POST /clients/:id/take-over` |
| Problem | A partner learns whether a client exists (404) and whether its responsible person is active (409), for clients they cannot see. |
| Impact | Search already reveals that a client exists. Every refusal is recorded as `client.take_over_refused`. |
| Fix | Accepted: this is how the agreed takeover works. |

### C8 — Nobody is told about a takeover

| | |
|---|---|
| Severity | **Informational** |
| Location | `ClientsService.takeOver` |
| Problem | A takeover is audited but not emailed to anyone. |
| Impact | Oversight depends on someone reading the audit log. |
| Fix | **Fixed after the review**, by decision of the project owner: every active compliance holder, except the partner who did it, is emailed who took over which client from whom. The client is named by reference only and the reason stays out: email passes through outside providers. Sent after the change commits. |
| Test | `clients.controller.spec.ts`: "telling compliance". Not sending, emailing the partner about their own takeover, or adding the reason to the email each fail a test. |

### C9 — Re-enabling a person does not return their clients

| | |
|---|---|
| Severity | **Informational** |
| Location | Takeover design |
| Problem | Once a client has been taken over, re-enabling the previous responsible person does not hand it back. |
| Impact | Intended: the partner who took it over is now accountable. Handing it back needs a takeover in the other direction once that person is disabled, or Matters teams. |
| Fix | None. Documented here. |

## Checked and sound

| Area | Result |
|---|---|
| Visibility rule | One function, `visibleTo`, used by every query that reads or changes client details or contacts. Removing it from any query fails a test, including a repository-level test for contacts |
| Not found vs forbidden | A client you may not see answers exactly like one that does not exist |
| Object references | A contact is always looked up with its client: another client's contact id through this client's address gives 404. **Tested** |
| Mass assignment | Every body is strict: `reference`, `createdBy`, `status`, `id`, `clientId`, `active` on creation, and the other kind's fields give 400 |
| Database rights | No `DELETE` anywhere. Reference, number, creator, kind and responsible person cannot be written by the app. Details cannot move to another client. **Tested with the app role** |
| Takeover rules | Enforced by a `SECURITY DEFINER` trigger with a fixed `search_path`, so no app bug can move a client without a history row, or from an active person. Removing the service's own check still leaves the database refusing. History rows cannot be changed or deleted by any role |
| Races | Edits lock the details row; takeovers queue on an advisory lock. Both races are forced on every run by holding the lock from another connection |
| Audit | Same transaction as each change; field names, ids and kinds only, never names, addresses or reasons. Rollback when the audit write fails is **tested** |
| Search input | `%`, `_` and `\` are matched literally; the query is parameterised; length 2 to 100; repeated parameters refused |
| Dates | `DATE` read as `YYYY-MM-DD` strings, so no time zone shifts a date of birth. **Tested** with 29 February |
| Countries | Checked against the ISO 3166 list; `UK`, `EU` and `SU`, which `Intl` accepts, are refused |
| Permissions | Pinned by `permissions.spec.ts`; administrators, accounts and compliance have no client permissions; clients have none |
| Error output | 500s carry a reference only; the database error logged for the null byte (now refused earlier) contained no value |
