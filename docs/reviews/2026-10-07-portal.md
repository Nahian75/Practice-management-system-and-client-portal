# Security review: client portal

**Date:** 2026-10-07
**Scope:** portal access, document sharing, the client-only API and client
screens (`apps/api/src/portal/`, migrations `0026` and `0027`, the sharing
parts of `apps/api/src/documents/`, and the `/portal` screens in `apps/web`).
Commits `436f3dd` to `9ab17b2`.
**Method:** code and database rules read; API and browser boundaries checked;
each finding reproduced with a regression test before its fix; every new
safeguard then broken on purpose and restored; focused tests run after the
restoration. The production dependency tree was checked from npm's local
advisory cache (`npm audit --offline --omit=dev`: no cached finding). An
up-to-date online advisory query was not authorised because it sends the
project's dependency list to npm.

## Findings

### P1 - Changing the address on record leaves the old login with access

| | |
|---|---|
| Severity | **High** |
| Location | `visibleInPortal` (`portal.repository.ts`) |
| Problem | A link's address was checked only when the link was created. Later requests checked that the account and link were active, and that an organisation contact was active, but not that the account's address was still the address on the client or contact record. |
| Impact | **Probe:** after changing an individual client's email address, the account at the old address could still list the matter and download its shared document. The same was true after changing an organisation contact's address. A corrected address or a contact whose mailbox changed hands could therefore leave the former address with confidential access indefinitely. |
| Fix | **Fixed after the review.** Every portal query now also requires the account email to equal the current individual-client or active-contact email. A mismatch removes that client's matters and documents on the next request. The link row remains as history; staff can end it and invite the new address. |
| Test | `portal.controller.spec.ts`, for both an individual and an organisation: matter details, document list and download become 404, and the matter leaves the list. Removing the two email comparisons made both tests fail with 200. |

### P2 - PostgreSQL does not re-check who is managing a portal link

| | |
|---|---|
| Severity | **Medium** |
| Location | `check_portal_link`, `check_portal_link_end` (migration `0026`) |
| Problem | The API checked that the actor could see the client before adding or ending a link. The database checked only that the recorded actor was a staff account. It did not require an active account, current responsibility for the client, or current membership of one of the client's matter teams at the write itself. |
| Impact | A removal, takeover or account disable racing with the API's earlier read could still be followed by the link write. A misuse of the application database role could also name any staff account as the actor. |
| Fix | **Fixed after the review** (migration `0028`). On both creation and ending, PostgreSQL requires the actor to be active staff who is either the client's responsible person or an active member of one of its matter teams. |
| Test | `portal.migration.spec.ts` writes directly as the application role and refuses disabled staff and staff who cannot see the client, for both creation and ending. Disabling the insert trigger made the creation test fail. |

### P3 - The owner can remove or rewrite portal-link history

| | |
|---|---|
| Severity | **Low** |
| Location | `portal_links` (migration `0026`) |
| Problem | The application role lacked delete and identity-update rights, but the table owner could delete a link. While ending an active link, the owner could also change its account, client, contact, creator or creation time. That contradicted the insert-and-end-only record rule. |
| Impact | Someone holding the migration credentials could erase or falsify who had client access. Those credentials are separate from the API, so this does not give a normal application request that power. |
| Fix | **Fixed after the review** (migration `0028`). A delete trigger refuses every role. The end trigger now compares every fixed field and permits only the first setting of `ended_at` and `ended_by`. |
| Test | `portal.migration.spec.ts` uses the owner connection and refuses both deletion and a changed creation time during ending. Disabling either trigger made its matching test fail. |

### P4 - A sharing/withdrawal race can miss the unshare audit event

| | |
|---|---|
| Severity | **Low** |
| Location | `DocumentsService.withdraw`, `DocumentsRepository.withdraw` |
| Problem | Withdrawal correctly made a shared document private inside PostgreSQL, under the document lock. The service decided whether to write `document.unshared` from a value read before that lock. If sharing completed between the read and withdrawal, the immutable sharing history contained the automatic unshare but the audit log did not. The opposite order could write an unshare audit event for no change. |
| Impact | Access remained safe, but the audit trail could disagree with the authoritative sharing history during a narrow race. |
| Fix | **Fixed after the review.** Withdrawal now takes the same document lock before reading the current sharing setting. It returns that locked value to the service, which records `document.unshared` only when the withdrawal trigger really changed the setting. |
| Test | `documents.controller.spec.ts` holds the advisory lock, queues sharing first and withdrawal second, then checks the two immutable sharing rows and all three audit events. Using the earlier, unlocked value made the unshare event disappear. |

### P5 - Accepted behaviour and later work

| | |
|---|---|
| Severity | **Information** |
| Items | **A request already authorised may finish** if access ends or a document is unshared immediately afterwards; the next request is refused, which is the stated rule. **Portal downloads are not separately rate-limited;** they require a live two-factor session, use unguessable ids and are audited. **Invitation email delivery** still has the persistent-outbox item F5 before production. Retention and disposal remain F3. |

## Checked and in order

- **Account separation:** `@ClientOnly()` covers the whole portal controller;
  permission routes imply `@StaffOnly()`. Direct tests give staff 403 on
  portal routes, clients 403 on staff document routes, and signed-out callers
  401. The two Next.js layouts redirect an account to its own side and the
  client layout has no staff links.
- **Portal links:** the database fixes the account, client, contact and actor at
  creation; matches the address on record; allows one active link per account
  and client; and permits one final end only. Disabled accounts, inactive
  contacts, changed addresses and ended links fail on the next request.
- **Matter data:** client responses contain only reference, title, type,
  status, opened date and active team names. Response schemas omit client ids,
  account ids, conflict checks, parties and internal fields.
- **Documents:** documents start private. Sharing changes are insert-only and
  made only by active matter-team staff. Portal queries require shared and not
  withdrawn, and return only the latest version. There is no client version
  parameter.
- **Downloads:** the API re-runs link, contact, address, account, sharing and
  withdrawal checks in the download query. Files are attachments with
  `nosniff`, `no-store` and a sandboxing Content Security Policy, and use the
  encrypted document vault. Every allowed client download records the client
  account and ids only.
- **Audit and privacy:** grant, end, share, unshare and download records carry
  ids and outcomes, never names, addresses, titles, file names or contents.
  Notifications for an existing portal user do not name the newly linked
  client.
- **Browser handling:** portal pages are rendered afresh with `no-store`; React
  escapes client and file text; nothing is kept in browser storage. Ending
  access between the matter and document reads leaves the page showing only
  the same plain message as an unknown matter.
- **Forged requests:** grant, end, share and unshare use changing HTTP methods
  covered by the API's cross-site request check. The session cookie is
  `__Host-`, secure in production, HTTP-only and same-site.
- **Database credentials:** the API still has only `pms_app`; migration-owner
  credentials are separate and not available to the running application.
