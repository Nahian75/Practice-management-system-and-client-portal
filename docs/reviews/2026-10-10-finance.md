# Security review: Finance module

**Date:** 2026-10-10  
**Scope:** time and rates, billing and credit notes, the bank register, ledgers,
client-money payments, statement import, reconciliation, Finance APIs, exports
and staff screens (`apps/api/src/finance/`, migrations `0042` to `0046`, and
the Finance parts of `apps/web`). The module was delivered in commits
`17619db` to `94db6d2`.  
**Method:** the current SRA Accounts Rules and accounting-record guidance and
HMRC VAT Notice 700/disbursement guidance were checked on 10 October 2026;
database functions, privileges, locks, encryption, queries, response schemas,
downloads and screens were read. Each confirmed issue received a regression
before its fix in migration `0047` or the application. New database safeguards
were then exercised against PostgreSQL. The production dependency tree was
checked from npm's local advisory cache (`npm audit --offline --omit=dev`: no
cached finding). No online npm advisory request was made because it would send
the dependency list to npm.

## Regulatory sources checked

- [SRA Accounts Rules](https://www.sra.org.uk/solicitors/standards-regulations/accounts-rules/),
  especially rules 8.1 to 8.4 on chronological client ledgers, a cash book with
  a running total, statements, five-week reconciliation and the central bill
  record.
- [SRA guidance on accurate client accounting records](https://www.sra.org.uk/solicitors/guidance/accurate-client-accounting-records/),
  including payment evidence, sufficient client funds, full client-balance
  lists, outstanding items and Compliance/manager review.
- [HMRC VAT Notice 700](https://www.gov.uk/guidance/vat-guide-notice-700),
  especially sections 16.3 and 18.2.3 on invoice and credit-note contents.
- [HMRC costs and disbursements guidance](https://www.gov.uk/guidance/vat-costs-or-disbursements-passed-to-customers).

The reviewed requirements remain consistent with the Finance design's SRA and
HMRC assumptions.

## Findings

### F1 - Finance-role revocation can race an already admitted money action

| | |
|---|---|
| Severity | **Medium** |
| Location | `assert_active_accounts`, `assert_active_compliance` |
| Problem | Finance functions rechecked the actor's active account and role but did not lock those rows. A concurrent role revocation or account disable could commit after the check while the financial action continued using the stale result. |
| Impact | **Probe:** holding an Accounts approval transaction open did not hold the role record on which it relied. This contradicted the rule that requesters, approvers, recorders and signers hold their role when the action is made. |
| Fix | **Fixed after the review** (migration `0047`). Both helpers now take shared locks on the account and qualifying role rows. Revocation/disable and the financial action are ordered at commit; every existing Finance function that calls the helpers inherits the safeguard. |
| Test | `payment.migration.spec.ts` proves Accounts revocation waits behind an in-progress approval. `reconciliation.migration.exclusive.spec.ts` proves the same for Compliance sign-off. Removing either `FOR SHARE` lets the matching race finish early. |

### F2 - A paid withdrawal can be dated before its approval

| | |
|---|---|
| Severity | **Medium** |
| Location | `client_payment_events`, `record_client_payment_event` |
| Problem | The workflow required an approved current state, but the supplied bank date only had to fall inside the bank account's history and not in the future. An approval made today could therefore be followed by a withdrawal recorded yesterday or years earlier. |
| Impact | **Probe:** with an older bank account, a refund approved today accepted yesterday's paid date and created backdated client-ledger and cash-book postings. The record then implied that four-eyes authority existed before the bank payment. |
| Fix | **Fixed after the review** (migration `0047`). A second database trigger runs after the existing state validation and refuses a paid date earlier than the immutable approval event's London calendar date. The whole payment transaction, postings and event roll back together. |
| Test | `payment.migration.spec.ts` backdates a bank outcome before approval, expects refusal and proves that no finance transaction remains. Removing the trigger makes the probe succeed. |

### F3 - Ledger and reconciliation records omit required balance detail

| | |
|---|---|
| Severity | **Medium** |
| Location | derived matter ledgers and cash books; client-account reconciliation snapshot |
| Problem | Lists returned amounts and a current aggregate but not the running balance at each posting. A reconciliation fixed only aggregate client liabilities, not the per-client/matter balance list behind the number. Later backdated entries could change a reconstructed list without changing the signed snapshot. |
| Impact | The firm could not produce the cash book running total or the exact immutable client-liability list reviewed by Compliance from Stass alone, despite SRA rule 8 and its accompanying guidance requiring those records. |
| Fix | **Fixed after the review.** Ledger queries now calculate stable signed running balances across all pages; screens and audited CSV exports show them. Migration `0047` adds an immutable per-matter client-balance snapshot whose positive rows must total the reconciliation's client-ledger figure. Reconciliation detail, export and Compliance screen show that list. |
| Test | Ledger HTTP tests check source/target and cross-page running balances and CSV columns. Reconciliation database/API tests check the exact fixed balance row, response/export, application-role insert denial and owner mutation denial. Breaking the correlated balance calculation or snapshot trigger fails those tests. |

### F4 - Generated VAT documents do not state numeric VAT rates

| | |
|---|---|
| Severity | **Medium** |
| Location | `billText`, `creditText`, credit-note response |
| Problem | A bill printed internal labels such as `standard`; a credit note printed only the VAT amount. Neither document gave the numeric rate for each credited line, and neither provided a VAT-rate breakdown. |
| Impact | A taxable bill or credit note downloaded for delivery could omit information required by HMRC VAT Notice 700, weakening the client's evidence for input-tax recovery. |
| Fix | **Fixed after the review.** Fixed bill and credit-note content now states `20%`, `5%`, `0%`, `Exempt` or `Outside scope`, gives quantity/extent and unit value, and includes net/VAT totals by treatment. Credit-note responses derive the original immutable line's VAT treatment. |
| Test | `billing.controller.spec.ts` checks numeric line rates, quantity/unit values, VAT breakdowns and the credit-note treatment field. Reverting the document formatter or repository join fails the regression. |

### F5 - Accepted behaviour and later work

| | |
|---|---|
| Severity | **Information** |
| Items | **Stass does not initiate bank payments.** Accounts records the external bank's outcome; the bank remains authoritative. **Disbursement classification remains a professional control.** The screen separates recharges and true disbursements and stores explicit VAT treatment, but Accounts must retain source evidence on the matter and verify HMRC's agency, benefit, authority and exact-cost conditions. **Backdated posting remains available where legitimate.** Receipts may be entered for an earlier open-account date and paid outcomes may use the approval date or later; immutable posted and audit times reveal when Stass learned the fact. **Request/download limiting and retention** remain deployment items F2 and F3. |

## Checked and in order

- **Money and posting integrity:** boundary values are exact decimal strings and
  PostgreSQL stores integer pence. Every transaction has the required balanced
  shape; client liabilities cannot become negative; reservations and matter,
  bill and bank locks prevent double spending.
- **Payment authority:** evidence, matter/client relationship, live bank
  accounts, available client funds and unpaid billed costs are rechecked under
  locks. Requester and approver differ and both are active Accounts holders.
  Encrypted payees are absent from lists, audit and terminal responses.
- **Reconciliation:** CSV is inert UTF-8 data with strict headers, row/size and
  amount bounds, duplicate fingerprints and opening/closing arithmetic.
  Matches are exact and reversed by history. Snapshots cover every open client
  bank account, totals, client liabilities and outstanding items; a different
  active Compliance holder signs the permanent record.
- **Billing:** issue and credit numbering is serialised; bill, credit and
  delivery snapshots are permanent; credit cannot exceed a line or erase a
  paid costs transfer. Downloads carry restrictive attachment headers.
- **Authorization and visibility:** client sessions cannot enter staff Finance;
  ordinary staff see only permitted matter time/bills; Accounts and Compliance
  receive their documented firm-wide and action-specific powers. Database
  functions repeat mutable actor and record rules.
- **Privacy and audit:** bank and payee details use AES-256-GCM with context
  binding and a key outside PostgreSQL. Sensitive names, account details,
  narratives, statement text and evidence stay out of audit metadata. Posted
  changes and their audit events share one transaction.
- **Dependencies:** the review added no dependency. The offline production
  advisory check found no cached vulnerability.

## Verification

- A clean PostgreSQL test database passed all 76 API test files and 1,635
  tests, including controlled Accounts/Compliance revocation races and owner-
  role immutability probes.
- API and web type-checks and production builds passed. The complete Playwright
  suite passed all 77 tests with four workers; its Finance journey covers the
  two-person payment, matched closing statements, frozen client balances and
  independent Compliance sign-off.
- The hidden-character scan and `git diff --check` passed.
