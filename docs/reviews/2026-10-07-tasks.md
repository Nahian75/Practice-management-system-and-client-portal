# Security review: tasks module

**Date:** 2026-10-07
**Scope:** task permissions, database records and history, the staff API and
the matter and task screens (`apps/api/src/tasks/`, migrations `0029` to
`0032`, and the task parts of `apps/web`). The module was delivered in commits
`e765321` and `1a4cb7f`.
**Method:** database rules, grants, queries, response schemas and screens read;
each confirmed finding reproduced in a database, HTTP and browser regression
before its fix; a controlled race used for the new row lock; every new
safeguard then broken on purpose and restored. The production dependency tree
was checked from npm's local advisory cache (`npm audit --offline --omit=dev`:
no cached finding). No online advisory query was made because that would send
the dependency list to npm.

## Findings

### T1 - Losing the partner role leaves supervisor-only task powers

| | |
|---|---|
| Severity | **Medium** |
| Location | `apply_task_change` (migration `0032`), `TasksRepository.findForChange`, task detail page |
| Problem | A supervising partner who lost the partner role stayed recorded as the matter's supervisor until another partner took over. If they still held the fee-earner role, the permission guard admitted the request. The API and PostgreSQL treated the stale team label alone as enough to complete, cancel or reopen tasks assigned to other people. The page offered those controls too. |
| Impact | **Probe:** after removing the partner role, the former partner could still complete another fee earner's task over HTTP. A direct application-role insert into `task_changes` was also accepted. They could alter the legal team's workflow and remove an open-task closure block despite no longer having supervisor powers. The permanent history and audit still named them, but did not prevent the change. |
| Fix | **Fixed after the review** (migrations `0033` and `0034`). A status change by someone other than the current assignee now requires the active supervising-team row, an active staff account and a current partner-role row. PostgreSQL locks the matter, task, membership, account and role in a fixed order, so a role removal and status change cannot pass one another. Migration `0034` preserves the older outside-team refusal without editing migration `0033` after it had been applied. The API repeats the current-role check and returns `canChangeStatus`; the page uses that answer instead of interpreting the team label itself. |
| Test | `tasks.migration.spec.ts` refuses the direct write and forces a role-removal race; `tasks.controller.spec.ts` gives the former partner `canChangeStatus: false` and 403; `tasks.spec.ts` removes the buttons and runs axe. Disabling the database trigger, removing the API role joins, or making the page infer from the team label made the matching test fail. |

### T2 - Accepted behaviour and later work

| | |
|---|---|
| Severity | **Information** |
| Items | **Task history is returned whole.** It grows only through deliberate, authenticated changes and every row is small; if real histories become long, pagination can be added without weakening the permanent record. **Task creation and changes have no module-specific rate limit.** They require a two-factor staff session, a current role and matter membership, and are audited; general request limiting remains deployment item F2. **Tasks remain staff-only.** They are deliberately absent from the client API and portal. Reminders remain for Notifications. |

## Checked and in order

- **Visibility:** every list, detail and change query requires current matter
  membership. A task outside the team and an unknown task both answer 404.
  Permission alone opens nothing; client sessions cannot enter staff routes.
- **Matter state and actors:** creation and every change require an open matter.
  Creators, assignees and change actors are active team members. Only the
  current assignee or an active supervisor still holding the partner role can
  change status.
- **Database records:** identity, initial status and creation time are set by
  PostgreSQL. Current values change only through insert-only history. Tasks and
  history cannot be updated, deleted or truncated, including by the owner.
  The app cannot supply before values, ids or times.
- **Concurrency:** creation locks the matter, membership and account rows;
  changes lock the matter and task plus every actor or assignee row they rely
  on. Closure uses the same matter lock and refuses any open task. Controlled
  races cover closure against creation, completion and reopening, and role
  removal against a supervisor status change.
- **Input and output:** request schemas are strict and text is checked again by
  database constraints. Response schemas send only declared task, person,
  history and capability fields. Task text is rendered by React, not as HTML.
- **Audit and privacy:** creation and each real change share their transaction
  with the audit event. Audit metadata has ids, priority, field names and
  states only, never task titles, descriptions or due dates. A failed audit
  write rolls back the task and history.
- **Browser handling:** pages are server-rendered with `no-store`; ids are
  encoded in paths; no task data is kept in browser storage. Closed matters are
  read-only and outsiders get the same plain screen as an unknown task.
- **Dependencies:** the review added no dependency. The offline production
  advisory check found no cached vulnerability.
