# Security review: matters module

**Date:** 2026-10-05
**Scope:** `apps/api/src/matters/`, `apps/api/src/clients/search-quota.ts`, the
matter-team branch of client visibility, `infra/postgres/init/02-extensions.sh`,
migrations `0016`–`0022`. Commits `39b672c`…`a003be9`.
**Method:** code read against the review checklist in the engineering rules;
each safeguard confirmed by breaking it on purpose during the build and checking
a test fails; probes against the real app and PostgreSQL with synthetic data.

## Findings

### M1 — Conflict checks compared every stored name in full

| | |
|---|---|
| Severity | **Medium** (availability) |
| Location | `app.find_possible_conflicts` (migration `0017`) |
| Problem | Each check called the normalising function on every stored name and compared it in full. No index could help. |
| Impact | **Probe:** a 20-name check took 5.5 seconds against about 10,000 individuals. The app's statement timeout is 15 seconds, so a larger firm, or a busier server, would get failed checks, and every check is a full scan. |
| Fix | **Fixed in this review.** Migration `0023`: trigram indexes on the normalised names, and a search that finds candidates through them (whole-name similarity of 0.1 or more, or the checked name 0.8 inside the stored one) before applying the unchanged rule. A first attempt combined all three trigram operators in one `OR` and became slower (15.6 seconds): one direction cannot use the index, and that made PostgreSQL scan every row. Measured after the fix: 1.2 seconds for 20 names. The results are identical to the full comparison on every probe set. The one narrowing: a short stored name inside a long checked name is found when it is at least about a tenth of it ("Acme" inside "Acme Trading International Holdings": 0.15). |
| Test | `matters.migration.spec.ts`: the indexed search returns the same total as comparing every name in full; a short stored name inside a longer checked name is still found. |

### M2 — Conflict checks reveal more client names per hour than search

| | |
|---|---|
| Severity | **Medium** |
| Location | `POST /conflict-checks` |
| Problem | A check may hold 20 names and returns up to 50 matches, and counts as one use of the hourly allowance shared with client search (60 an hour). The total match count is also returned. |
| Impact | **Probe:** three checks with common surnames and company words returned 104 distinct client names. At 60 checks an hour that is up to about 3,000 names an hour, against 1,200 through search. The counts reveal firm-wide totals (one check reported 94,142 possible matches). |
| Fix | **Fixed after the review**, by decision of the project owner: each name checked is one unit of the 60-an-hour allowance; a search is one. The allowance sums `units` from the audit records (`AuditService.sumUnitsRecent`). A check that does not fit is refused whole. The client's own name, added by the database, is free. |
| Test | `matters.controller.spec.ts`: three 20-name checks use the hour; a check that does not fit is refused and nothing is recorded, while a smaller one goes through. Removing the units fails a test. |

### M3 — Matter references can be confirmed through supervision takeover

| | |
|---|---|
| Severity | **Low** |
| Location | `POST /matter-supervision-takeovers` |
| Problem | References are sequential (`C-000123/001`). A partner gets 409 for a reference that exists and 404 for one that does not. |
| Impact | **Probe:** 20 real references all answered 409; a made-up one 404. A partner can list which matters exist, but nothing about them. Every refusal is recorded as `matter.supervision_takeover_refused`. |
| Fix | Accepted: the takeover needs to name matters the partner cannot see, and the refusals are audited. |

### M4 — Compliance access has no rate limit

| | |
|---|---|
| Severity | **Medium** |
| Location | `POST /matter-compliance-accesses` |
| Problem | Each access is recorded, audited and emailed to the supervising partner, but nothing limits how many. |
| Impact | **Probe:** a compliance account read 20 matters in 0.4 seconds. A misused or taken-over compliance account could read every matter in minutes; the emails would show it afterwards, scattered across supervising partners. |
| Fix | **Fixed after the review**, by decision of the project owner: at most 30 accesses per person per hour, counted from the audit records under a per-person lock; the 31st gets 429. Reaching the limit is recorded once an hour as `matter.compliance_access_limited` and emailed to every other compliance holder and every administrator, naming the person, not any matter. |
| Test | `matters.controller.spec.ts`: "hourly limit (review M4)". 35 accesses sent at once give exactly 30 answers. Removing the lock or the alert fails a test. |

### M5 — Adding other parties after opening is not built

| | |
|---|---|
| Severity | **Low** (gap) |
| Location | Matters design |
| Problem | Parties are recorded only when a matter opens. A new opponent later in a matter cannot be added. |
| Impact | Staff will keep that information outside the system, where it is not conflict-checked. |
| Fix | **Open:** a new party on an open matter needs a new conflict check, and possibly clearance again; to be designed with the project owner. |

### M6 — Two partners can act at the same moment across a handover

| | |
|---|---|
| Severity | **Informational** |
| Location | Clearance (clearance lock) and handover (team lock) |
| Problem | A clearance and a handover by the same partner, sent at the same moment, take different locks; the clearance can commit as the partner stops supervising. |
| Impact | The partner was the supervising partner when they acted; both are recorded. |
| Fix | None. |

### M7 — Later modules must respect `awaiting_clearance`

| | |
|---|---|
| Severity | **Informational** |
| Location | Design |
| Problem | "Nothing can be added while awaiting clearance" holds today because nothing can be added to a matter yet. |
| Fix | Documents, tasks, time and bills must refuse work on a matter awaiting clearance, in the database as well as the API. Noted in `matters.md`. |

## Checked and sound

| Area | Result |
|---|---|
| Visibility | Every matter query takes a filter: the team (`visibleTo`) or one recorded compliance access (`reachedByComplianceAccess`). There is no unfiltered read. Removing the filter from any query fails a test |
| Client visibility | Responsible person or active team member; removing someone from a team removes the client from them at once. **Tested** |
| Status changes | The app cannot write a matter's status. Opening, clearance, closure and takeover go through `SECURITY DEFINER` triggers with fixed `search_path`; with each service check removed, the database still refused |
| Conflict checks | Matches are found by the database when the check is recorded; the app cannot write them. Checks are single use, for one client, by one person, for 24 hours. Every party must have been checked |
| Teams | Exactly one active supervising partner at every commit; members hold the right roles; history kept; closed matters cannot change |
| Races | Numbering, clearance, takeover and team changes are serialised; the clearance race and the ten-at-once numbering are forced on every run |
| Audit | Same transaction as each change; ids, roles, counts and field names only. Titles, names checked and reasons stay out |
| Notices | Clearance, takeover and compliance access emails name the matter by reference only, never the reason |
| Mass assignment and input | Strict bodies; references validated by pattern; safe-text rule on titles, names and reasons, in the API and the database |
| Exhaustiveness | Team-change answers end in `satisfies never`, so an unanswered result fails to compile |
| Extensions | Installed by the superuser into a schema nobody else can write to; the migration role still cannot install anything |

## Not in scope

The web app, documents and time recording, and AML checks before opening.

## Test data

The test database keeps every row from every run (the app role cannot delete),
now tens of thousands of names. That made two conflict-check assertions flaky
and slows the suite. **Done**, by decision of the project owner:
`npm run db:reset-test` (`infra/postgres/reset-test-database.sql`) recreates
`pms_test` empty, without touching the development database. After the reset
the suite took 38 seconds instead of about 80, and every migration applied
cleanly to an empty database. One test that relied on leftover rows now makes
its own.
