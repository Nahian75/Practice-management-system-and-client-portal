# Security review: staff web app

**Date:** 2026-10-05
**Scope:** `apps/web/` (pass-through to the API, Content Security Policy and
headers, server-side reads, every screen built in steps 9a to 9e), and the parts
of the API it depends on: client address handling (`TRUSTED_PROXIES`), response
headers, email sending. Commits `ed67d56`…`70a0907`.
**Method:** code read; each safeguard confirmed by breaking it on purpose during
the build and checking a test fails; probes against the built web app and API
with synthetic data, as the end-to-end tests run them; Next.js's own forwarding
code read (`next/dist/server/base-server.js`,
`next/dist/server/lib/router-utils/proxy-request.js`); `npm audit`.

## Findings

### W1 — A browser can choose the address the API records for it

| | |
|---|---|
| Severity | **High** if deployed as it is now |
| Location | The `/api` pass-through (`src/proxy.ts`), `TRUSTED_PROXIES=loopback` in the API |
| Problem | Next.js fills in `X-Forwarded-For` only when the request has none (`??=`), and its rewrite passes the header on unchanged, without adding the address the request came from. The API trusts the web app, on the same machine, to report the address. So the address the API uses is whatever the browser wrote. The web app also listens on every network interface (`next start`, `next dev`). |
| Impact | **Probe:** a failed sign-in sent with `X-Forwarded-For: 203.0.113.77` was recorded under 203.0.113.77. Anyone reaching the web app directly can get round the per-address sign-in limit (trying passwords across many accounts) and put false addresses in the audit log and on sessions. The per-account limits still apply. |
| Fix | **Fixed after the review.** (1) The web app listens on `127.0.0.1` only, in development and production, so nothing reaches it except through the machine itself. (2) Deployment rule: a TLS reverse proxy on the same machine is the only way in, and puts the address it received the connection from last in `X-Forwarded-For`. The API, trusting only loopback, then takes that address and ignores anything the browser wrote before it. (3) A test that fails if the start scripts stop binding to `127.0.0.1`. The proxy cannot be fixed inside the web app: it never learns the connection's address. |
| Test | `e2e/listening.spec.ts`: the tests start the web app with its real `start` script; it accepts connections on `127.0.0.1` and refuses them on every other address of the machine, and both scripts name `127.0.0.1`. Removing `--hostname` from the start script fails both tests. |

### W2 — API answers with personal data may be kept in the browser's cache

| | |
|---|---|
| Severity | **Medium** |
| Location | Every API response; the browser reaches them through `/api` |
| Problem | The web app's pages are sent with `Cache-Control: no-store`; the API's answers are sent with no `Cache-Control` at all, and with an `ETag`. A browser may store such answers on disk and check them again later. |
| Impact | **Probe:** client details (`GET /api/clients/:id`) and client search results came back without `Cache-Control`. On a shared or lost computer, client names and details could stay in the browser's cache after sign-out. |
| Fix | **Fixed after the review.** The API sends `Cache-Control: no-store` on every answer, errors included, set once in `configureApp`. Sign-out also sends `Clear-Site-Data: "cache"`, so the browser drops anything already kept. |
| Test | `app.setup.spec.ts` and `auth.controller.spec.ts` (API); `clients.spec.ts` and `sign-in.spec.ts` (browser, through the pass-through). Removing either header fails a test. |

### W3 — The API's internal address is shown to the browser

| | |
|---|---|
| Severity | **Low** |
| Location | `/api` answers |
| Problem | Next.js adds an `x-middleware-rewrite` header naming where it sent the request, for example `http://127.0.0.1:3101/clients/<id>`. |
| Impact | Reveals the API's host and port. They are not reachable from outside once W1 is fixed, so this only helps someone already on the machine. |
| Fix | **Fixed after the review**, as a deployment rule: the reverse proxy from W1 removes the header ([deployment.md](../deployment.md)). The web app cannot remove it: Next.js reads it to carry out the rewrite. |

### W4 — No error or "not found" pages of the app's own

| | |
|---|---|
| Severity | **Low** |
| Location | `src/app/` |
| Problem | There is no `error.tsx` or `not-found.tsx`. Next.js's defaults are shown: they leak nothing (probe: no stack trace or message in a 404 or a failed page), but they are unbranded, and [web.md](../web.md) says error pages "show a reference", which they do not. |
| Fix | **Fixed after the review.** `app/error.tsx` shows Next.js's error reference (`digest`) and nothing else; `app/not-found.tsx` serves addresses with no page and malformed ids, with status 404. |
| Test | `e2e/error-pages.spec.ts`, against a second copy of the web app whose API cannot be reached: the page answers 500 with the reference, and none of the error's words, address or port. Hiding the reference fails the test. |

### W5 — Invitations are emailed before the request answers

| | |
|---|---|
| Severity | **Information** |
| Location | `InvitationsService.invite` (API) |
| Problem | Inviting and re-enabling send the email during the request; other emails go through the outbox. A slow mail server makes these requests slow (seen in testing with four parallel workers). |
| Fix | Accepted: if the mail server is down, the administrator sees the invitation fail instead of believing it was sent; the link exists only in that email. The outbox becoming a persistent queue before production is already tracked in `mail-outbox.ts`. |

## Checked and in order

- **Pass-through paths.** Only `/api/` is passed on, to a fixed address with the path set, not joined as text. Probes: `/api//evil.example`, `/api/%2fevil.example`, `/api/%2e%2e/health`, `/api/..%2fhealth`, `/API/health`, `/apix/health` all stay on the API or the web app and answer 404 (`/api/./health` is normalised to `/health`).
- **Content Security Policy.** A fresh nonce per page; no `unsafe-inline` or `unsafe-eval` in production; tests fail on any violation, and a deliberately added inline style was caught.
- **Headers on pages.** `no-store`, `nosniff`, `X-Frame-Options: DENY`, `frame-ancestors 'none'`, `no-referrer`, COOP, Permissions-Policy, HSTS in production; the framework is not advertised.
- **Session and forged requests.** The `__Host-session` cookie is set and checked by the API only; the web app never reads it in the browser. Browser requests reach the API from the same site, so the API's `Sec-Fetch-Site` check applies unchanged. No Next.js server actions are used.
- **Server-side reads.** `apiGet` sends only the session cookie, paths come from the app's code, and identifiers from the address are encoded. Reads the API audits (client search, compliance access) are sent from the browser so the record has the person's address; server-side reads are not audited and carry no address-based limits.
- **Tokens.** Invitation and reset links carry their token after `#`; the page removes it from the address bar and history at once (tested).
- **No open redirect.** After sign-in the app always goes to `/`; there is no "return to" parameter. Sign-out loads the sign-in page in full, so nothing stays in the page's memory.
- **Browser storage.** Nothing is kept in `localStorage` or `sessionStorage`. A compliance access result is held only in the page's memory.
- **Access decisions.** Every screen shows what the API returned; hidden buttons are for clarity only, since the API refuses the action whatever the screen shows. Browser tests cover the refusals for client takeover, matter team and closing pages, and staff changes.
- **Dependencies.** `npm audit --omit=dev`: no known vulnerabilities. Next.js 16.3.6 includes the fix for the middleware-bypass flaw of 2025 (`x-middleware-subrequest`).
